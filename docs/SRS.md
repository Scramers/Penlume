# Penlume 软件需求规格（SRS）

> 版本：0.3  
> 状态：Typora 1.14.9 功能对齐基线  
> 适用范围：Phase 0、MVP、Beta、v1.0

## 1. 需求约定

### 1.1 优先级

| 优先级 | 含义 |
|---|---|
| P0 | 对所属里程碑具有阻塞性，未通过不得发布 |
| P1 | 重要需求；允许在预览构建中暂缺，但必须在所属里程碑完成 |
| P2 | 增强需求，可根据资源调整 |

### 1.2 里程碑

| 标识 | 含义 |
|---|---|
| M0 | Phase 0 技术验证 |
| MVP | Windows 单文件写作闭环 |
| Beta | 日常写作功能完整，提供三平台测试构建 |
| V1 | 三平台公开发布 |

### 1.3 基准测试环境

MVP 的量化指标使用以下最低基准环境：

- Windows 11 x64。
- 四核 CPU，基础频率不低于 2.5 GHz。
- 8 GB 内存。
- SSD。
- 1920×1080 分辨率，100% 或 125% 缩放。
- 关闭开发者工具，使用发布构建。

测试文档：

| 编号 | 规模 | 内容 |
|---|---|---|
| DOC-S | 100 KB、约 1,000 行 | 标题、段落、列表、链接和代码块混合 |
| DOC-M | 1 MB、约 10,000 行 | 基础语法混合，包含中英文和长代码块 |
| DOC-L | 2 MB、约 20,000 行 | 压力测试文档，不作为所有 MVP 功能的流畅保证 |

## 2. 功能需求

所有功能需求同时受 [Typora 功能对齐矩阵](TYPORA_PARITY.md) 约束。原 MVP/Beta 标识继续表示实现先后，不再表示最终产品可以缺少后续对齐项。

| 编号 | 需求 | 优先级 | 里程碑 | 验收条件 |

| FR-FILE-006 | 使用同目录临时文件和原子替换保存 | P0 | MVP | 模拟写入/替换失败时原文件保持可读，编辑内容仍可恢复 |
| FR-FILE-007 | 为未保存编辑写恢复草稿 | P0 | MVP | 停止输入 1 秒内完成草稿计划，最坏恢复丢失窗口不超过 2 秒 |
| FR-FILE-008 | 启动时发现并处理恢复草稿 | P0 | MVP | 用户可恢复、另存为或丢弃；任何选择均不静默覆盖原文件 |
| FR-FILE-009 | 检测文件外部修改 | P0 | MVP | 外部写入后 2 秒内检测；自身保存事件不误报 |
| FR-FILE-010 | 处理本地编辑与外部修改冲突 | P0 | MVP | 提供重新加载、覆盖、另存为；默认按钮不得是覆盖 |
| FR-FILE-011 | 支持非 UTF-8 文件的安全处理 | P1 | Beta | 无法可靠解码时以只读或明确确认方式打开，不得乱码后覆盖 |
| FR-FILE-012 | 文件夹工作区和文件树 | P1 | Beta | 可打开文件夹、浏览 Markdown 文件并刷新外部变化 |
| FR-FILE-013 | 标签页管理多个文档 | P1 | Beta | 每个标签独立维护 dirty、草稿和冲突状态 |
| FR-FILE-014 | 操作系统文件关联 | P1 | Beta | 双击支持的文件可聚焦已有实例或打开新文档 |

文件行为的详细状态机以 [文件安全规范](FILE_SAFETY.md) 为准。

### 2.3 Markdown 保真

| 编号 | 需求 | 优先级 | 里程碑 | 验收条件 |
|---|---|---:|---|---|
| FR-SOURCE-001 | 无修改保存不得重写文件 | P0 | MVP | 打开后直接保存，文件 SHA-256 与修改时间均不改变 |
| FR-SOURCE-002 | 已编辑文档满足语义保真 | P0 | MVP | 保存后重新解析得到与编辑器状态等价的支持语法树 |
| FR-SOURCE-003 | 不支持语法不得静默删除 | P0 | MVP | 兼容测试中的保护语法在相邻编辑和保存后仍存在 |
| FR-SOURCE-004 | 保留原文件 LF/CRLF 和 UTF-8 BOM 属性 | P1 | Beta | 保存后换行风格和 BOM 状态与打开时一致 |
| FR-SOURCE-005 | 未触碰块保持源码文本不变 | P1 | V1 | 编辑单个块后，测试夹具中其他块字节保持一致 |
| FR-SOURCE-006 | 建立自动化 round-trip 测试集 | P0 | M0 | M0 不少于 30 个样例，MVP 不少于 80 个，V1 不少于 200 个 |

保真级别、规范化规则和语法范围以 [Markdown 兼容规范](MARKDOWN_COMPATIBILITY.md) 为准。

## 4. MVP 发布门槛

MVP 发布必须同时满足：

1. 所有标记为 P0/MVP 的功能需求通过。
2. 所有 P0 非功能需求通过。
3. 不存在已知的数据丢失、静默覆盖或无法恢复的阻塞问题。
4. Markdown 自动化测试集不少于 80 个样例。
5. 中文 IME 手工矩阵在微软拼音下通过。
6. Windows 干净环境安装与文件读写冒烟测试通过。
7. 许可证扫描没有未决的高风险依赖。

## 5. 需求变更规则

- 新增 MVP 功能必须同时移除同等工作量的非安全功能，或重新批准范围。
- 数据安全、安全隔离和 Markdown 不破坏原则不得以赶进度为由降级。
- 修改 P0 需求时必须同步修改对应规范、测试和里程碑。
- 编辑器内核、文件保存策略和支持方言的改变必须通过 ADR 记录。
